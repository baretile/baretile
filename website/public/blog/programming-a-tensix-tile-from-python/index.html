Programming a Tensix tile from Python

Adding two arrays is a small enough operation to follow all the way through an accelerator.

We'll put two 32x32 arrays in a Tensix tile's local memory, build the programs that unpack, add, and pack their values, then read the answer back into Python. We'll see how Python constructs hardware instructions and how three programs coordinate to produce one result.

We'll use Baretile and Tenstorrent's ttsim simulator. You can run the example without a card. Baretile hasn't been tested on hardware yet, and simulator timings don't predict card performance.

Python runs on the host. It builds instruction words and generates small C programs for the chip's RISC-V cores. Clang compiles those programs, and Baretile loads and launches them.

One worker, three programs

A Tensix tile contains local memory, small RISC-V cores, and a coprocessor with units for moving and computing on data. For this example, we need the local memory, called L1, and three parts of the coprocessor: the unpackers, matrix unit, and packers. The matrix unit supports elementwise addition as well as matrix multiplication. Tenstorrent's architecture reference describes the full tile.

Our data follows this path:

SrcA and SrcB hold the operands where the matrix unit can read them. Dst holds the result before it is packed back into L1.

Baretile assigns three RISC-V cores to direct these operations:

CoreProgram
TRISC0Unpack the inputs into SrcA and SrcB
TRISC1Add the operands and write Dst
TRISC2Pack Dst back into L1

These programs run concurrently. Their instructions must wait for the data and storage they need.

Run the example

To follow along, you need Python 3.12 or later, clang with a RISC-V target, lld, and the Blackhole simulator library. Download libttsim_bh.so from the ttsim v1.11.5 release, then prepare a checkout:

git clone https://github.com/baretile/baretile
cd baretile
git checkout 6ddd68493551eaeea3079f8a1793b51f00d4814f
export TTSIM=/absolute/path/to/libttsim_bh.so

Keep TTSIM set: it selects the simulator. Without it, Baretile tries to open a physical card.

The Python blocks below, in order, form a complete script. Save them as add.py in the checkout, or download the complete script.

First, open the simulator, create a runtime, and select its first worker:

import struct

from baretile import bh, pci
from baretile.chip import Chip
from baretile.runtime import Runtime, compile_kernel
from baretile.tensix import (
    MATH_END, from_bf16, kernel_config, math_begin,
    math_program, pack, pack_program, slot_base,
    to_bf16, tt, unpack, unpack_program,
)

chip = Chip(pci.open_device())
rt = Runtime(chip)
x, y = rt.cores[0]

a = [[float((r * 32 + c) % 7 - 3) for c in range(32)]
     for r in range(32)]
b = [[float((r + 2 * c) % 5 - 2) for c in range(32)]
     for r in range(32)]

Both arrays contain small integers represented as floating-point values. We'll store them in bfloat16, a 16-bit floating-point format. These inputs and their sums are exactly representable, so we can check the answer with an exact comparison.

Put the inputs in memory

Before writing the inputs, we need to arrange them as Baretile expects.

The word tile has two meanings here. A Tensix tile is the hardware unit running our programs. A tensor tile is a block of values. This example uses one Tensix tile to add two tensor tiles.

Baretile stores each 32x32 tensor tile as four 16x16 faces:

Each face is stored row by row, with the four faces placed consecutively in memory. The first 256 values belong to face 0, the next 256 to face 1, and so on.

This layout gives the math unit rows of 16 values to operate on. A complete tensor tile becomes 64 such rows.

We can calculate an element's position and write its bfloat16 representation into L1:

def tile_index(r, c):
    face = (r // 16) * 2 + c // 16
    return face * 256 + (r % 16) * 16 + c % 16


def to_l1(slot, matrix):
    words = [0] * 1024
    for r in range(32):
        for c in range(32):
            words[tile_index(r, c)] = to_bf16(matrix[r][c])
    address = slot_base("bf16") + slot * 2048
    chip.write(x, y, address, struct.pack("<1024H", *words))


to_l1(1, a)
to_l1(2, b)

A bfloat16 tile occupies 2,048 bytes: 1,024 values at two bytes each. We put the inputs in slots 1 and 2 and reserve slot 3 for the result. These slots are Baretile's convention for addressing tile-sized regions of L1.

Build an instruction

The inputs are now in memory. Next, we need instructions that operate on them.

A Tensix instruction is a 32-bit word. In Baretile's encoding table, the opcode occupies the top byte, and named fields describe the remaining bits. An instruction encoder can therefore be a small Python function:

def ins(name, **fields):
    opcode, layout = bh.TENSIX_OPS[name]
    word = opcode << 24
    for name, value in fields.items():
        first, width = layout[name]
        assert 0 <= value < 1 << width
        word |= value << first
    return word


add = ins("ELWADD", dst=0)
print(hex(add))
print(tt([add]))

This prints:

0x28000000
asm volatile(".word 0xa0000000" ::: "memory");

ELWADD is the elementwise addition instruction. Calling ins constructs its encoding as a Python integer.

The second line shows how that instruction reaches the coprocessor. The RISC-V cores support a custom instruction encoding that pushes a Tensix instruction into their associated thread's queue. That encoding is the Tensix word rotated left by two bits. Baretile's tt function emits it through a .word directive inside C inline assembly. Tenstorrent documents this mechanism as .ttinsn.

Clang compiles the surrounding C program. When a TRISC executes the embedded word, it submits the addition instruction to the coprocessor.

Coordinate the three programs

One ELWADD handles an 8x16 block. Our tensor tile contains 64 rows of 16 values, so we need eight addition instructions to cover it. The instruction reference describes the operation and its Blackhole encoding.

Here are the instruction sequences for all three programs:

unpacks = unpack(1, 2)

adds = [ins("SETRWC", bit_mask=0b1111)]
adds += [ins("ELWADD", dst=0) for _ in range(7)]
adds += [ins("ELWADD", dst=0, clear_dvalid=3)]

maths = math_begin(False) + adds + MATH_END
packs = pack("h", 3)

unpack(1, 2) selects the two L1 slots and emits instructions to load them into SrcA and SrcB. The unpackers mark the source banks ready when the data is available. Addition waits for that handoff before reading the operands.

The math sequence starts with SETRWC, which resets the row counters. Baretile configures the address mode to advance the source and destination counters by eight rows after each addition. Although each instruction says dst=0, that field is an offset added to the current destination counter. The instructions therefore write successive parts of the result.

The final addition sets clear_dvalid=3, releasing both source banks so the unpackers can reuse them.

The operations around adds manage the destination:

  • math_begin(False) waits for available output space and selects the destination region. False means it doesn't clear that region first; these additions overwrite their output.
  • MATH_END waits for the math to finish, then posts a semaphore indicating that a result is ready.
  • pack("h", 3) waits for that semaphore, writes the result to L1 slot 3 in bfloat16, and releases the destination space.

Here, "h" refers to a variable in the generated C programs. It selects the starting row in Dst and begins at zero.

These waits connect three independently executing programs. Without the handoff from math to pack, for example, the packer could read Dst before the additions had finished.

Compile and launch

We can now wrap the instruction sequences in complete device programs:

kernel = compile_kernel(
    None,
    unpack_program(tt(unpacks), kernel_config()),
    math_program({}, tt(maths)),
    pack_program(tt(packs)),
)

rt.launch(kernel, (), 1)
rt.wait()

The program helpers supply the entry points, configuration, and initialization. kernel_config() selects the data formats and memory layout. The unpack program initializes the shared configuration and semaphores; the math and pack programs wait for that setup before running their bodies.

compile_kernel accepts programs for BRISC, TRISC0, TRISC1, and TRISC2, in that order. We pass None for the BRISC kernel because the host has already placed the inputs in L1. A larger tensor kernel would use BRISC to move data between DRAM and L1.

The runtime compiles and loads the programs. The final argument to launch requests one unit of work, which runs on the first worker we selected earlier. wait() waits for the kernel to complete.

Read the answer

At this point, the result is in L1 slot 3. Reading it back reverses the conversion we used for the inputs:

def from_l1(slot):
    address = slot_base("bf16") + slot * 2048
    words = struct.unpack("<1024H", chip.read(x, y, address, 2048))
    return [
        [from_bf16(words[tile_index(r, c)]) for c in range(32)]
        for r in range(32)
    ]


got = from_l1(3)
expected = [[a[r][c] + b[r][c] for c in range(32)]
            for r in range(32)]

assert got == expected
print("all 1024 sums match")

The comparison checks every element, including the boundaries between faces. Because we chose small, exactly representable values, a mismatch here cannot be explained by ordinary bfloat16 rounding.

Use the tensor API

Baretile's tensor API builds kernels using the same instruction helpers. We can ask it to perform the addition and compare its answer with our handwritten kernel:

from baretile.tensor import Tensor

A = Tensor.of(rt, a)
B = Tensor.of(rt, b)
assert (A + B).tolist() == got
print("Tensor result matches the handwritten kernel")

In this version, the tensor inputs live in device DRAM. The generated kernel also includes the BRISC program that brings them into L1 and writes the result back. Calling tolist() runs the computation and returns the values to Python.

Run the complete script from the checkout:

python3 add.py

It prints:
